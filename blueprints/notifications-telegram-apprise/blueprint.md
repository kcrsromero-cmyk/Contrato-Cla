## 1. Project Overview & Non-Goals

### Vision

Contrata360 is a Colombian public-procurement analytics platform. An Express API and a BullMQ worker
in `backend/` ingest SECOP open data through Socrata, and users follow entities and contracts from the
frontend. Users can already store notification preferences (`notifyEmail`, `notifyTelegram`,
`notifySms`, `telegramUsername`), but nothing sends a notification and nothing knows a Telegram chat to
send one to. This change adds a **decoupled, replaceable Notifications module**: a `Notifier` port with
a registry of adapters, a first adapter that delivers to Telegram through the Apprise API container
already running in the compose stack, and a Telegram linking flow. In that flow a user asks the API
for a short code, sends `/start <code>` to the project's Telegram bot, and the worker's long-polling
gateway stores that user's `chat_id`. A test endpoint proves the whole path end to end.

The module copies the ports-and-adapters pattern already proven in `backend/src/modules/identity/`:
`IdentityProvider` (port), `IdentityProviderRegistry` (static `Map` registry, default name), and
`SupabaseIdentityProvider` (adapter). Swapping Telegram-via-Apprise for email or SMS later is one new
adapter and one `NotifierRegistry.register` call, with no change to the service or the routes.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| Registered Contrata360 user (procurement analyst, supplier following entities) | Link their Telegram chat once, then trigger a test notification to confirm delivery | Once to link, occasionally to re-test |
| Operator deploying through Coolify | Set the bot token, deploy, and confirm the migrator applied the migration and the worker is polling | Once per deploy |
| Future backend developer | Add an email or SMS `Notifier` adapter without touching the service or the routes | Per new channel |

### Target state

After this change, in the repo's own conventions:

- `backend/src/modules/notifications/{domain,application,infrastructure,presentation,__tests__}` exists,
  shaped like `identity/`.
- `Notifier` is the port. `NotifierRegistry` is the static registry (default name `apprise`).
  `AppriseNotifier` POSTs to `${APPRISE_URL}/notify/` with `tgram://<token>/<chat_id>`.
- `NotificationService` sends to a user's linked Telegram chat and issues link codes.
  `NotificationChannelNotLinkedError` is the typed refusal.
- `TelegramLinkGateway` (a Telegram-specific concern, **not** a `Notifier`) long-polls `getUpdates`
  in the **worker** process, matches `/start <code>`, stores `users.telegram_chat_id` and clears the
  code. It stops inside the existing `gracefulShutdown` `Promise.all`.
- Two authenticated routes: `POST /api/v1/notifications/telegram/link-code` and
  `POST /api/v1/notifications/test`.
- `users` gains three nullable columns and one unique index, through one additive migration that the
  existing `migrator` service applies.
- `EnvSchema` gains `TELEGRAM_BOT_TOKEN` (required), `TELEGRAM_BOT_USERNAME` (optional, default `''`)
  and `APPRISE_URL` (default `http://apprise:8000`). Compose passes the two Telegram variables to
  `backend` and `worker`.

### Goals — this change

1. A user can obtain a single-use, 15-minute Telegram link code from the API, and the bot deep link
   when the bot username is configured.
2. The worker binds the user's Telegram `chat_id` when that code arrives as `/start <code>`, and only
   while the code is unexpired.
3. A user with `notifyTelegram = true` and a linked chat receives a test message through Apprise. Any
   other user gets a 409 that explains what is missing.
4. Notification channels are replaceable behind one port, with the registry pattern the identity
   module already uses.

## 4. Data Model

### Entities

**User** (`users`) — an existing entity. This change adds three nullable columns that hold the
Telegram link state. Only the delta and the frozen neighbours are shown. Every other `User` field is
untouched.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `telegramUsername` → `telegram_username` | `String?` | existing, FROZEN | Free-text handle the user typed in their profile. **Not** used for delivery: Telegram bots cannot message a username, only a `chat_id` |
| `notifyTelegram` → `notify_telegram` | `Boolean` | existing, FROZEN, default `false` | The user's opt-in. `NotificationService` refuses to send when it is `false` |
| `telegramChatId` → `telegram_chat_id` | `String?` | NEW, nullable | The Telegram `chat.id` (decimal, may be negative for groups), stored as text. Set only by `TelegramLinkGateway` |
| `telegramLinkCode` → `telegram_link_code` | `String?` | NEW, nullable, **unique** | The current single-use link code: 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. Set by `POST /notifications/telegram/link-code`, cleared to `NULL` once linked |
| `telegramLinkCodeExpiresAt` → `telegram_link_code_expires_at` | `DateTime?` | NEW, nullable | Issue time + 15 minutes. A code with `expiresAt <= now` is ignored. Cleared to `NULL` once linked |

**Lifecycle of the link columns:**

1. `link-code` sets `code` and `expiresAt`. A second call overwrites both, so only the latest code
   is valid.
2. `/start <code>` before `expiresAt` sets `telegramChatId = String(chat.id)` and clears `code` and
   `expiresAt` to `NULL`.
3. An expired code is ignored and stays until the next `link-code` call overwrites it.

Re-linking a different chat repeats the same flow, and `telegramChatId` is overwritten.

### Relationships

No new relationship. The three columns are scalars on `users`. Existing `User` relations
(`organization`, `plan`, `favorites`, `favoriteEntities`) and their cascade behaviour are unchanged.

### Indexes

| Table | Index | Why |
|---|---|---|
| `users` | `users_telegram_link_code_key` — UNIQUE on `telegram_link_code` | `TelegramLinkGateway` looks a user up by code (`findUnique({ where: { telegramLinkCode } })`). Uniqueness also guarantees one code maps to one user. A collision on issue surfaces as Prisma `P2002`, and the service retries |

Postgres UNIQUE allows many `NULL`s, so every unlinked or already-linked user, whose code is `NULL`,
coexists.

### Migrations

**Tool:** Prisma Migrate. Production applies migrations **only** through the existing `migrator`
compose service (`command: sh scripts/migrate.sh` → `npx prisma migrate deploy`), which `backend` and
`worker` wait on (`condition: service_completed_successfully`). No build step applies a migration to
any database.

**This migration is hand-authored, following the repo's own convention.** Several existing
migrations (`20260818000000_…`, `20260820000000_…`, `20260820100000_add_notification_prefs_to_user`,
`20260821000000_…`, `20260821100000_…`) carry hand-picked round timestamps and hand-written
`ADD COLUMN IF NOT EXISTS` SQL. This change does the same. The directory name is chosen by the step,
not by a tool. It sorts after the newest existing migration (`20260921000000_make_object_entityname_nullable`),
so `migrate deploy` applies it last:

`backend/prisma/migrations/20261120000000_add_telegram_notification_fields/migration.sql`, exactly:

```sql
-- Additive and nullable only: Telegram linking for the notifications module.
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "telegram_chat_id" TEXT;
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "telegram_link_code" TEXT;
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "telegram_link_code_expires_at" TIMESTAMP(3);
CREATE UNIQUE INDEX IF NOT EXISTS "users_telegram_link_code_key" ON "users"("telegram_link_code");
```

`TEXT` and `TIMESTAMP(3)` are what Prisma maps `String?` and an un-annotated `DateTime?` to on
Postgres. `users_telegram_link_code_key` is Prisma's `<table>_<column>_key` name for a single-field
`@unique`, so the schema and the database agree and a later drift check stays clean (§20.1).

**Why not `prisma migrate dev --create-only`?** It needs a reachable Postgres plus the right to create
a shadow database. It replays all existing migrations, and if it detects drift it stops on an
interactive reset prompt. Each of those hangs or fails an unattended build. The hand-authored file
matches the repo's convention and is checked offline in step 3. The decision is recorded in §20.3.

**Production rule:** expand-only. The migration adds nullable columns and an index and touches no
existing column, so old code runs against the new schema unchanged, and rollback never has to
contract (§12). Never edit an existing migration directory.

## 5. API Design

### Conventions

- Base path: `/api/v1` (`API_PREFIX` in `backend/src/server.ts`). This module mounts at `/api/v1/notifications`.
- Response envelope: success responses are plain JSON objects (repo convention, no `data` wrapper).
  Errors are `{ "error": string }`, as everywhere in the repo. This module **adds** a machine-readable
  `"code"` string on its 409 and 502 responses. Validation failures keep the existing
  `validateRequest` shape `{ "error": "Validation failed", "details": … }`.
- Error codes this module emits:

  | HTTP | `code` | When |
  |---|---|---|
  | 400 | — (existing `Validation failed` shape) | Request body is not an empty object |
  | 401 | — (`{ "error": … }`) | Missing or invalid `Authorization`, or no resolvable user |
  | 409 | `TELEGRAM_NOT_LINKED` | `POST /test` for a user with no `telegramChatId`, or no `users` row |
  | 409 | `TELEGRAM_DISABLED` | `POST /test` for a linked user whose `notifyTelegram` is `false` |
  | 429 | — (`{ "error": … }`) | More than 5 requests per minute per IP on this router |
  | 502 | `DELIVERY_FAILED` | Apprise returned non-2xx, or the request to Apprise failed |
  | 500 | — (`{ "error": "Internal Server Error" }`) | Anything else |

- Validation: zod schemas in `presentation/NotificationSchemas.ts`, applied with the existing
  `validateRequest` from `identity/presentation/ValidationMiddleware.ts`.
- Pagination: NOT APPLICABLE — no list endpoints.
- Idempotency: `POST /telegram/link-code` is deliberately **not** idempotent. Each call issues a new code
  and invalidates the previous one, so the latest code wins. `POST /test` sends one message per call and
  is rate-limited rather than deduplicated.
- Rate limits: the existing global limiter (500 per 15 minutes per IP), plus a router limiter of
  **5 requests per 60 s per IP** on both routes, using the repo's `FallbackRedisStore` with prefix
  `rl:notifications:`.

### Routes

| Method | Path | Description | Auth | Rate limit |
|---|---|---|---|---|
| POST | `/api/v1/notifications/telegram/link-code` | Issue a fresh 8-character link code (15-minute TTL) and the bot deep link when configured | user (Bearer JWT) | 5/min/IP + global |
| POST | `/api/v1/notifications/test` | Send a fixed test message to the caller's linked Telegram chat | user (Bearer JWT) | 5/min/IP + global |

No public or unauthenticated route is added.

### Critical endpoints — full detail

#### `POST /api/v1/notifications/telegram/link-code`

- Middleware chain, in order: `authMiddleware.handle` → `currentUserResolver.resolve` →
  `notificationsLimiter` → `validateRequest(EmptyBodySchema)` → `controller.createTelegramLinkCode`.
- Request body: none, or `{}`. `EmptyBodySchema = z.strictObject({})`, so any key → 400.
- Success **200**:

  ```json
  { "code": "ABCD2345", "expiresAt": "2026-11-20T10:15:00.000Z", "botDeepLink": "https://t.me/ContrataBot?start=ABCD2345" }
  ```

  - `code`: 8 characters matching `^[A-HJ-NP-Z2-9]{8}$`.
  - `expiresAt`: ISO-8601 UTC, issue time plus 15 minutes.
  - `botDeepLink`: `https://t.me/<TELEGRAM_BOT_USERNAME>?start=<code>`, or `null` when
    `TELEGRAM_BOT_USERNAME` is the empty string.
- Errors:
  - 401 `{ "error": "Missing or invalid Authorization header" }` (from `AuthMiddleware`).
  - 401 `{ "error": "Unauthorized" }` when `req.user` is absent after the resolver.
  - 400 validation shape.
  - 429.
  - 500.
- Side effects: one `prisma.user.update` setting `telegramLinkCode` and `telegramLinkCodeExpiresAt`.
  On Prisma `P2002` (code collision) it retries with a fresh code, 3 attempts in total, then responds
  500. Nothing is sent to Telegram.

#### `POST /api/v1/notifications/test`

- Middleware chain: `authMiddleware.handle` → `currentUserResolver.resolve` → `notificationsLimiter` →
  `validateRequest(EmptyBodySchema)` → `controller.sendTest`.
- Request body: none, or `{}`.
- Behaviour: `NotificationService.sendToUser(user.id, TEST_NOTIFICATION_MESSAGE, TEST_NOTIFICATION_TITLE)`, where
  - `TEST_NOTIFICATION_TITLE = 'Contrata360'`
  - `TEST_NOTIFICATION_MESSAGE = 'Notificación de prueba: tu cuenta de Telegram está vinculada correctamente con Contrata360.'`
- Success **200** `{ "delivered": true }`.
- Errors:
  - 409 `{ "error": <message>, "code": "TELEGRAM_NOT_LINKED" }`, where `<message>` is
    `NotificationChannelNotLinkedError.message` for that reason (literal strings in step 4).
  - 409 `{ "error": <message>, "code": "TELEGRAM_DISABLED" }`.
  - 502 `{ "error": "No se pudo entregar la notificación. Inténtalo de nuevo más tarde.", "code": "DELIVERY_FAILED" }`.
  - 401, 400, 429 and 500 as above.
- Side effects: one HTTP `POST` to Apprise. On 502 the controller logs
  `logger.warn('Notification delivery failed', { userId, status })`, where `status` is the Apprise
  HTTP status or `undefined`. It never logs the request URL or body, because the Apprise URL contains
  the bot token.

#### Outbound contract — Apprise stateless notify (consumed by `AppriseNotifier`)

- `POST ${APPRISE_URL without trailing slashes}/notify/`, header `Content-Type: application/json`.
- Body: `{ "urls": "tgram://<TELEGRAM_BOT_TOKEN>/<chat_id>", "body": <message>, "title": <title> }`.
  `title` is omitted when `undefined`.
- Any 2xx = delivered. Any other status → `NotificationDeliveryError(message, status)`.
- The trailing slash on `/notify/` is deliberate. It is the form the Apprise API README documents, and
  it works whether or not the server also accepts the slashless form.

#### Outbound contract — Telegram Bot API `getUpdates` (consumed by `TelegramLinkGateway`)

- `GET https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getUpdates` with query
  `offset=<n>&timeout=25&allowed_updates=["message"]`, built with `URLSearchParams`.
- Response `{ "ok": true, "result": [ { "update_id": number, "message"?: { "text"?: string, "chat": { "id": number } } } ] }`.
- After each batch the next `offset` is `max(update_id) + 1`. That acknowledges the batch to Telegram.
- The text accepted as a link request is `/start <code>` or `/start@<BotName> <code>`. The code is
  case-insensitive on input, upper-cased, then checked against `^[A-HJ-NP-Z2-9]{8}$`.

  `authRouter`.
- **Added:** outbound calls to Apprise (API process) and the Telegram Bot API (worker process).
- **Modified:** nothing in any existing route, middleware or response.

## 8. Authentication & Authorization

### Provider and rationale

The existing Supabase-issued JWT, verified by `jwtValidator` (JWKS at `AUTH_JWKS_URL`). Both new routes
reuse the exact chain `procurement/presentation/routes.ts` uses, so this change introduces no new
authentication surface.

### Flows

- **Authenticated request.** `AuthMiddleware.handle` rejects a missing or non-`Bearer` header with 401
  and verifies the JWT. `CurrentUserResolver.resolve` fetches the user through the identity provider,
  upserts the `users` row and attaches `req.user`. On any failure it calls `next()` without a user,
  and the controller then answers 401 `{ "error": "Unauthorized" }`.
- **Telegram linking** (authorization by possession of a short-lived secret):
  1. The authenticated user calls `link-code`.
  2. The code is shown to that user only.
  3. The user sends `/start <code>` to the bot from the Telegram account they want to link.
  4. The worker binds that `chat.id` to the user who owns the code.
  5. The code is single-use: cleared on success, unusable after 15 minutes.
- **Failure branches:** unknown code → ignored. Expired code → ignored. Malformed text → ignored.
  Nothing is written in any of those cases. No reply is sent to Telegram (reply messages are a
  non-goal).

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| `POST /api/v1/notifications/telegram/link-code` | authenticated user | `backend/src/modules/notifications/presentation/routes.ts` (`authMiddleware.handle`) and `NotificationsController.createTelegramLinkCode` (`req.user` check) |
| `POST /api/v1/notifications/test` | authenticated user, and only that user's own chat | same file and `NotificationsController.sendTest`. The user id always comes from `req.user.id`, never from the body |

**Enforcement rule:** authorization is checked server-side on every request. There is no client-side
surface in this change.

### Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| `USER` (any authenticated user, any plan) | Issue a link code for their own account. Send a test notification to their own linked chat | Target another user's id. Read any `telegram_chat_id` or link code (neither is ever returned except the caller's own fresh code) |

No capability gate (`requireCapability`) is added. The feature is available on every plan. That
follows from the signed-off architecture, which names no plan restriction.

### Sessions

Unchanged: bearer tokens issued by Supabase, validated per request. No cookies, so no CSRF surface on
these routes.

### Multi-tenancy / row-level isolation

Every query this module runs is keyed by `req.user.id` (API) or by the unique link code (worker).
There is no tenant-scoped data and no cross-user read.

## 9. BUILD ORDER

### The rules of a step

1. **One sitting per step.** Agent success rate drops sharply and non-linearly with task length, and
   long steps are where builds fail. If a step touches more than **5 files**, carries more than
   **6 acceptance criteria**, or needs more than one round of design thinking, split it. A step
   carries **2–6** acceptance criteria, with one happy path and at least one failure path at the low
   end.
2. **Every step carries all four fields:** `Do`, `Done when`, `Verify`, `Checkpoint`.
   `Checkpoint` is a literal shell block that commits and tags:
   `git add -A && git commit -m "<task-id>: <short description>"` then `git tag step-NN-slug`. The
   task id is the step's `tasks.json` id (`E1-T1` … `E2-T7`), and the description is that task's
   title, so the message is the same one the epic file's Checkpoint uses.
3. **"Done when" conditions are observable and machine-checkable**, in EARS form: **WHEN** trigger
   **THE SYSTEM SHALL** observable response.
4. **"It looks right" is banned**, and so are *works*, *is implemented* and *is wired up*.
5. **`Verify` is literal shell**, run from the repository root, and its exit status enforces the
   result.
6. **A step is not done until its own verify commands pass** *and* the previous steps' still do.
7. **Checkpoint every step.** If a step goes wrong, run `git reset --hard <previous step's tag>` and
   retry. For step 1 the previous tag is `notifications-baseline`, which §10 Bootstrap creates.
8. **Never skip ahead.** If step N is blocked, stop and report.
9. **No step retroactively breaks an earlier gate.** Env validation is the canonical risk here.
   `TELEGRAM_BOT_TOKEN` becomes required in step 1, so every test that loads `env.ts` either mocks it
   (`vi.mock('…/config/env', …)`) or sets the variable itself. Adapters take their configuration
   through constructor options, so no later step's unit test needs a real environment. §10's
   *Required by step* column agrees.
10. **Counts are counted.** The two counts asserted below — 2 compose services carrying the Telegram
    lines, and 5 workers plus 5 queues in `worker.ts` — were counted from `docker-compose.yml` (the
    `backend` and `worker` services, the only two that set `APPRISE_URL`) and from `worker.ts`
    lines 43–59. Every other gate asserts a property.
11. **Every `Verify` line exits 0 on a correct step.** Expected non-zero exits are wrapped as
    `status=0; cmd || status=$?; test "$status" -eq N`.
12. **Every check is observable in its medium.** Type-only facts are checked by `tsc`, runtime facts
    by vitest, file facts by `grep`/`test -f`.
13. **The first served endpoint is exercised in its own step.** Step 11's supertest suite drives the
    real router through Express. Step 11 also `require`s the first built notifications module from
    `dist/`, and step 12 does the same for the built gateway.
14. **No `Verify` asserts its own Checkpoint's state.** The `git diff -U0 HEAD -- <file>` lines below
    compare the working tree against the **previous** step's commit, which exists, and assert zero
    removed lines. They do not assert anything is committed.
15. **No byte-exact golden files.** Tests assert parsed JSON objects, status codes and `code` fields,
    never runtime-produced strings (§19.6).
16. **No gate passes on a bare non-zero exit.** Each expected failure asserts its specific code (`grep`
    1 = no match, and 2 = error now fails the gate).

#### Step 9 — Add the getUpdates long-poll loop

**Do**

Edit `backend/src/modules/notifications/infrastructure/TelegramLinkGateway.ts`. Add these members:

- `private offset = 0`, `private running = false`, an `AbortController` for the current run, and the
  loop promise.
- `async pollOnce(): Promise<void>`:
  1. Build `https://api.telegram.org/bot${botToken}/getUpdates?` + `new URLSearchParams({ offset: String(this.offset), timeout: String(pollTimeoutSeconds), allowed_updates: '["message"]' })`.
  2. Call `fetchImpl(url, { signal })`, where `signal` is the controller that `stop()` aborts.
  3. If `!response.ok`, throw `new Error(\`Telegram getUpdates responded ${response.status}\`)`. The
     message never includes the URL or the token.
  4. Parse `{ ok, result }`. If `ok` is not `true`, throw `new Error('Telegram getUpdates returned ok=false')`.
  5. Handle each update in order: `try { await this.handleUpdate(u) } catch (e: any) { logger.error('Telegram update handling failed', { updateId: u.update_id, error: e?.message }) }`,
     then `this.offset = u.update_id + 1`. A poison update can never block the cursor.
- `start(): void`. If already running, return. Otherwise set `running = true`, create a fresh
  `AbortController`, and start `loop()` without awaiting it, keeping the promise.
- `private async loop()`. While `running`:
  1. `await pollOnce()`.
  2. On error, caught as `catch (e: any)` (the repo's convention, as in `backend/src/worker.ts`): if `!running`, break (an abort during stop). Otherwise log
     `warn('Telegram getUpdates failed', { error: e?.message })` and sleep `errorBackoffMs`, with a
     sleep that resolves early when the controller aborts.
- `async stop(): Promise<void>`. Set `running = false`, abort the controller, and await the loop
  promise. A second call resolves at once.
- `fetchImpl` defaults to the global `fetch`. The default `pollTimeoutSeconds` stays `25`, below the
  worker's 30-second shutdown timeout, and `stop()` aborts the in-flight request rather than waiting
  it out.

## 14. Security & Secrets

| Concern | Control | Implemented in |
|---|---|---|
| Secret storage | `TELEGRAM_BOT_TOKEN` lives only in the Coolify env and the local untracked `.env` files. `.env.example` carries a blank value | Coolify, `.env.example`, `backend/.env.example` |
| Secret rotation | If leaked, use `@BotFather` → `/revoke`, update Coolify, redeploy. The old token stops working at once | operator procedure (§20.1) |
| Token leakage through logs | The token appears in two places: the Apprise `urls` body field and the `getUpdates` URL path. Neither is ever logged. `AppriseNotifier` contains no logging call (step 5 gate), and gateway and adapter error messages carry only HTTP status codes | `AppriseNotifier.ts`, `TelegramLinkGateway.ts` |
| Input validation | `z.strictObject({})` on both route bodies. The Telegram chat id is validated as `^-?\d+$` before it is put into the Apprise URL. The `/start` payload is upper-cased and checked against `^[A-HJ-NP-Z2-9]{8}$` before any query | `NotificationSchemas.ts`, `AppriseNotifier.ts`, `TelegramLinkGateway.ts` |
| Output encoding / XSS | JSON only. No HTML is rendered | — |
| SQL injection | Prisma parameterized queries only. The migration is static SQL | `NotificationService.ts`, `TelegramLinkGateway.ts` |
| AuthN / AuthZ | See §8. The user id always comes from `req.user.id` | `routes.ts`, `NotificationsController.ts` |
| CSRF | Bearer-token auth without cookies, so no CSRF surface | — |
| Rate limiting / abuse | 5 requests per minute per IP on both routes (`rl:notifications:`), plus the global limiter. This stops `/test` being used to spam a chat, and stops code churn | `routes.ts` |
| Link-code guessing | 32⁸ ≈ 1.1 × 10¹² codes, a 15-minute TTL, single use (cleared on link), and a unique index. A successful guess only binds the guesser's chat to the victim's account, which would mean receiving the victim's test notifications. The space makes that impractical | `domain/TelegramLinkCode.ts`, `NotificationService.ts` |
| Webhook verification | NOT APPLICABLE — no inbound webhooks (long polling only) | — |
| Dependency audit | No new dependencies. `(cd backend && npm audit --omit=dev)` stays a manual check, as today | — |
| Security headers | Unchanged (`helmet()` in `server.ts`) | `server.ts` |
| PII handling | `telegram_chat_id` is a personal identifier, stored in `users`, never returned by any endpoint and never logged (logs carry `userId` only). Its retention follows the `users` row. There is no account-deletion flow in scope | `schema.prisma`, `TelegramLinkGateway.ts` |
| Logging hygiene | Never log the bot token, a link code, a chat id, a request URL or a request body in this module | `.claude/rules/notifications-module.md` |

**Hard rules**

- No secret is ever committed, printed in a log, or returned in a response.
- All authorization checks run before the work: the controller checks `req.user` before calling the
  service.
- Nothing in this change parses an inbound third-party payload as trusted. `getUpdates` responses are
  pulled over TLS from `api.telegram.org` and validated field by field.

Regulated data: none beyond ordinary personal data (a Telegram chat id). The product operates in
Colombia under Ley 1581 de 2012 (habeas data). This change stores one more identifier for a purpose
the user explicitly initiates by sending `/start <code>`.

## Architecture

**Processes.** One codebase, three processes:
- `backend/src/server.ts` — the HTTP API (`backend` service).
- `backend/src/worker.ts` — BullMQ workers plus the Telegram link gateway (`worker` service).
- `migrator` — a one-shot `prisma migrate deploy`.

**Request path.** client → `server.ts` (helmet → `blockedPathsMiddleware` → global limiter → cors → `express.json` → morgan → `AuditMiddleware`) → `modules/<m>/presentation/routes.ts` (`authMiddleware.handle` → `currentUserResolver.resolve` → limiter → `validateRequest(schema)` → controller) → `modules/<m>/application/*Service.ts` → `modules/<m>/infrastructure/*` adapter or `infrastructure/db/prisma.ts` → Postgres / external HTTP.

**Module layout** — every module under `backend/src/modules/<name>/`:

| Layer | Holds | May import | Must never |
|---|---|---|---|
| `domain/` | pure interfaces, types, errors, constants | other `domain/` files, `node:` built-ins | Prisma, Express, `config` |
| `application/` | business logic services | `domain/`, own `infrastructure/*Registry`, `import type` from `@prisma/client` | `config`, Express |
| `infrastructure/` | concrete adapters + a static `*Registry` | `domain/`, `logger` | `config` (adapters take options in the constructor) |
| `presentation/` | `routes.ts`, controllers, zod `*Schemas.ts` | everything above, `config`, identity's `AuthMiddleware` / `CurrentUserResolver` / `ValidationMiddleware` | editing another module's files |
| `__tests__/` | vitest tests for that module | anything, with `vi.mock` | the network, a database |

**Ports and adapters.** `identity/` is the reference: `domain/IdentityProvider.ts` (port) → `infrastructure/IdentityProviderRegistry.ts` (static `Map`, `register(name, x)`, `resolve(name?)` with a default) → `infrastructure/SupabaseIdentityProvider.ts` (adapter). `notifications/` mirrors it with `Notifier` → `NotifierRegistry` (default `apprise`) → `AppriseNotifier`.

# Notifications module

- Layout mirrors `backend/src/modules/identity/`: `domain/` (port, errors, link-code constants) → `application/NotificationService.ts` → `infrastructure/` (`NotifierRegistry`, `AppriseNotifier`, `TelegramLinkGateway`) → `presentation/` (`routes.ts`, `NotificationsController.ts`, `NotificationSchemas.ts`).

- Only `presentation/routes.ts` imports `config`. Adapters and the gateway take `baseUrl` / `botToken` through constructor options.
