## 1. Project Overview & Non-Goals

### Vision

Contrata360 is a Colombian public-procurement analytics platform: an Express + Prisma API and a
BullMQ worker in `backend/` over SECOP open data. Plans (`FREE`, `STARTER`, `PROFESIONAL`,
`ENTERPRISE`) grant capabilities that controllers and `requireCapability` read from
`req.user.capabilities`. Today every protected route needs a browser session (a Supabase JWT), the
analytics module is unreachable for every plan because `USE_ANALYTICS` is never seeded, and there is
no way to switch a feature off in production without a deploy.

This change adds four things and nothing else:

1. **FeatureFlag** — a generic, default-open, database-only kill switch (`feature_flags` table,
   `requireFeatureEnabled(key)` middleware) wired to notifications, analytics and API-key access.
2. **ApiKey** — machine-to-machine access with `Authorization: Bearer ck_live_…`. The API-key path
   produces **exactly the `AuthenticatedUser` shape `CurrentUserResolver` produces**, so controllers
   and `requireCapability` need zero changes. Keys are minted, listed and revoked by a logged-in web
   session only.
3. **BUSINESS plan** — a new tier between PROFESIONAL and ENTERPRISE that grants API access.
4. **USE_ANALYTICS fix** — seed the capability the analytics routes already require.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| BUSINESS / ENTERPRISE customer integrating Contrata360 into their own systems | Mint an API key once in a session, then call procurement and analytics endpoints from scripts and ERPs | Daily, automated |
| PROFESIONAL / BUSINESS / ENTERPRISE web user | Use the analytics endpoints that were unreachable before this change | Weekly |
| Operator | Turn notifications, analytics or all API-key traffic off with one SQL `UPDATE`, without a deploy | Rarely, during incidents |

### Target state

- `feature_flags` table with rows `NOTIFICATIONS`, `ANALYTICS`, `API_ACCESS` (all `enabled = true`).
  `backend/src/modules/platform/` holds the keys, `isFeatureEnabled` and `requireFeatureEnabled`.
- `api_keys` table; `plans.api_requests_per_minute` column; capabilities `USE_ANALYTICS` and
  `USE_API`; plan `BUSINESS`.
- Identity gains the API-key domain, service, user mapper, middleware, per-key limiter, the combined
  `authenticateApiKeyOrSession` entry point, and session-only `/api/v1/auth/api-keys` routes.
- The 7 protected procurement routes and the 12 analytics routes accept either a session or an API
  key. Public routes stay public. Notifications and `/auth/*` stay session-only.

### Goals — this change

1. An operator can disable notifications, analytics, or all API-key traffic with one SQL statement,
   and a flag that was never created changes nothing.
2. A BUSINESS or ENTERPRISE user can mint an API key in a session, see it once, list and revoke it,
   and call every protected procurement and analytics route with it under the same plan rules as
   their session.
3. API-key traffic is rate-limited per key at the owning plan's `api_requests_per_minute`.
4. PROFESIONAL, BUSINESS and ENTERPRISE users can reach the analytics routes.

| Payments | NOT APPLICABLE — BUSINESS is inert data until an operator assigns it | — |

**Boundary rules**

- **Why a `platform` module for feature flags.** Three modules consume the flag middleware
  (notifications, analytics, identity). Putting it in `identity` would make an operational toggle
  look like an auth concern; `backend/src/infrastructure/` holds technical adapters (db, redis,
  security, logger), not business toggles. A tiny module with the standard layer split keeps the
  pure lookup (`application/isFeatureEnabled.ts`, `isPlanActive`-style plain function, testable with
  a fake client) apart from the Express/Prisma wiring (`presentation/requireFeatureEnabled.ts`,
  `requireCapability`-style factory).
- **Why API-key code lives in `identity`.** It produces `AuthenticatedUser` and sits next to
  `AuthMiddleware`/`CurrentUserResolver`. Express middleware goes in `presentation/` (where both of
  those live); the business rules go in `application/ApiKeyService.ts`; constants and errors in
  `domain/`.
- `domain/` imports only `domain/` files and `node:` built-ins. `application/` imports `domain/` and
  **type-only** `@prisma/client`; it never imports `prisma`, `config`, `logger` or Express.
- `presentation/` may import `prisma`, `logger`, `redisAppClient`, `FallbackRedisStore`.
  New cross-module imports allowed by this change: any module's `presentation/` may import
  `platform/presentation/requireFeatureEnabled` and `identity/presentation/apiKeyAuth`;
  `identity/presentation/ApiKeyAuthMiddleware.ts` imports `platform/domain/featureFlags`.
- **Never edit** `AuthController.ts`, `CurrentUserResolver.ts`, `AuthMiddleware.ts`,
  `AuthenticatedUser.ts`, `requireCapability.ts`, `server.ts`, `worker.ts`, `docker-compose.yml`,
  any `.env.example`, `backend/package.json` or `backend/package-lock.json`.
- The resolution convention (relative, extensionless specifiers, no alias, `node:` built-ins) is
  reconciled in §19.6's *Resolution convention matrix*.

## 4. Data Model

### Entities

**FeatureFlag** (`feature_flags`) — NEW. One row per operational kill switch. Created by the seed,
toggled only by SQL, never deleted by code.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `key` → `key` | `String` | PK | `NOTIFICATIONS`, `ANALYTICS`, `API_ACCESS` |
| `enabled` → `enabled` | `Boolean` | not null, default `true` | `false` makes `requireFeatureEnabled(key)` answer 503. A **missing row counts as enabled** (default-open) |
| `description` → `description` | `String?` | nullable | Human note for operators |
| `createdAt` → `created_at` | `DateTime` | default `now()` | — |
| `updatedAt` → `updated_at` | `DateTime` | `@updatedAt`, not null, no DB default | Prisma sets it; a hand-written `INSERT` must supply it (§12 runbook) |

**ApiKey** (`api_keys`) — NEW. A machine credential owned by one user. Lifecycle: created (plaintext
shown once) → used (`last_used_at` updated) → revoked (`revoked_at` set, row kept). Deleted only by
the cascade when its user is deleted.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` → `id` | `String @db.Uuid` | PK, `@default(uuid())` (client-side) | Public identifier used in `DELETE /api-keys/:id` |
| `userId` → `user_id` | `String @db.Uuid` | FK → `users.id`, `ON DELETE CASCADE`, indexed | Owner |
| `keyHash` → `key_hash` | `String` | unique | Lowercase hex SHA-256 of the full plaintext (64 chars) |
| `keyPrefix` → `key_prefix` | `String` | not null | First 12 chars of the plaintext (`ck_live_` + 4 random chars), stored unhashed so a user can recognize a key in a list. 4 random base64url chars leak 24 of 256 bits |
| `name` → `name` | `String` | not null | User label, 1–100 chars after trim |
| `createdAt` → `created_at` | `DateTime` | default `now()` | — |
| `lastUsedAt` → `last_used_at` | `DateTime?` | nullable | Set fire-and-forget on each successful authentication |
| `revokedAt` → `revoked_at` | `DateTime?` | nullable | Non-null = rejected with 401 |

**Plan** (`plans`) — EXISTING, one column added.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `apiRequestsPerMinute` → `api_requests_per_minute` | `Int?` | NEW, nullable | Requests per minute per API key. `NULL` = no limit configured; the limiter then applies the fallback of 10 (never unlimited). Every plan that grants `USE_API` gets a value in the seed |

**User** (`users`) — EXISTING, inverse relation only: `apiKeys ApiKey[]`. No column changes.

## 5. API Design

### Conventions

- Base path: `/api/v1` (`API_PREFIX` in `server.ts`, unchanged).
- Response envelope: plain JSON objects (repo convention, no `data` wrapper). Errors are
  `{ "error": string }`; this change's new errors add a machine-readable `"code"`. Existing error
  bodies are frozen.
- New error codes:

  | HTTP | `code` | Raised by | Body `error` |
  |---|---|---|---|
  | 503 | `FEATURE_DISABLED` | `requireFeatureEnabled(key)`, and `ApiKeyAuthMiddleware` when `API_ACCESS` is off | `Esta funcionalidad está deshabilitada temporalmente. Intenta de nuevo más tarde.` |
  | 401 | `INVALID_API_KEY` | malformed, unknown or revoked API key | `La clave de API es inválida o fue revocada.` |
  | 403 | `API_ACCESS_NOT_IN_PLAN` | valid key whose owner's resolved plan lacks `USE_API` | `Tu plan actual no incluye acceso por API.` |
  | 403 | `SESSION_REQUIRED` | an API key sent to `/api/v1/auth/api-keys` | `Las claves de API no pueden administrar claves de API. Usa tu sesión de la aplicación web.` |
  | 404 | `API_KEY_NOT_FOUND` | revoke of a key id that is malformed, missing, or another user's | `Clave de API no encontrada.` |
  | 429 | — | per-key limiter | `Demasiadas solicitudes con esta clave de API. Intenta de nuevo en un minuto.` |

- Validation: zod 4 through the existing `validateRequest(schema)` (400 `{ error: 'Validation failed', details }`).
- Pagination: NOT APPLICABLE — a user's key list is small and returned whole.
- Idempotency: `DELETE /api-keys/:id` is idempotent (an already-revoked key returns 200 unchanged).
- Rate limits: API-key requests get a per-key limiter (`rl:apikey:`, window 60 s, limit = owner's
  `apiRequestsPerMinute`, fallback 10); key management gets 10/min per IP (`rl:api-keys:`). Both use
  `FallbackRedisStore`. Existing limiters unchanged.

### Authentication detection rule (exact)

A request is on the **API-key path** if and only if `req.headers.authorization` starts with the
exact, case-sensitive string `Bearer ` **and** the remainder starts with `ck_live_`. Every other
request — no header, `Bearer eyJ…` (any JWT), `bearer ck_live_…`, `Basic …`, `Bearer  ck_live_…`
with two spaces — takes the **session path** unchanged, which keeps answering exactly as today
(e.g. 401 `{ error: 'Missing or invalid Authorization header' }`). An API-key-path token that is not
a well-formed key (`^ck_live_[A-Za-z0-9_-]{43}$`) is a 401 `INVALID_API_KEY`; it never falls back to
the session path. A Supabase JWT can never take the API-key path because a compact JWS begins with
`eyJ`.

### Critical endpoints — full detail

#### `POST /api/v1/auth/api-keys`

Chain: `requireSessionAuth` → `authMiddleware.handle` → `currentUserResolver.resolve` →
`apiKeysLimiter` → `requireCapability('USE_API')` → `validateRequest(CreateApiKeySchema)` →
`ApiKeyController.create`.

- Request: `{ "name": string }` — `z.strictObject({ name: z.string().trim().min(1).max(100) })`.
- 201: `{ "id": uuid, "name": string, "keyPrefix": string, "createdAt": ISO-8601, "key": "ck_live_…" }`.
  `key` is the only time the plaintext ever leaves the server.
- 403 `SESSION_REQUIRED` when the header is an API key (checked before any JWT parsing).
- 401 from the existing session chain when there is no valid session.
- 403 `{ error: 'Forbidden: Requires USE_API capability' }` (existing `requireCapability` body).
- 400 `{ error: 'Validation failed', details }` for a missing, empty, over-long or extra field.
- Side effect: one `api_keys` row with `key_hash`, `key_prefix`, `name`, `user_id`.

#### `GET /api/v1/auth/api-keys`

Session only, no capability (a downgraded user can still see and revoke old keys). 200
`{ "apiKeys": [{ id, name, keyPrefix, createdAt, lastUsedAt, revokedAt }] }`, newest first. Never
`keyHash`, never the plaintext.

#### `DELETE /api/v1/auth/api-keys/:id`

Session only, no capability. `:id` not shaped like a UUID → 404. Key not found **or owned by another
user** → 404 `API_KEY_NOT_FOUND` (never 403, so the existence of another user's key id is not
confirmed). Active key → sets `revoked_at = now`, 200 with the summary. Already revoked → 200 with the
unchanged summary.

#### Any API-key request to a protected procurement or analytics route

`authenticateApiKeyOrSession` → API-key path, in order:

1. `ApiKeyAuthMiddleware.handle`: flag `API_ACCESS` off → 503 `FEATURE_DISABLED` (before any key
   lookup). Token not matching the pattern → 401 `INVALID_API_KEY`. `findUnique({ where: { keyHash },
   include: { user: { include: { plan: { include: { capabilities: { include: { capability: true } } } } } } } })`;
   no row or `revokedAt` set → 401. Build the user with `ApiKeyUserMapper` (same plan rules as a
   session, FREE fallback included). Resolved capabilities lack `USE_API` → 403
   `API_ACCESS_NOT_IN_PLAN`. Otherwise attach `(req as any).user` (an `AuthenticatedUser`) and
   `(req as any).apiKey = { id, apiRequestsPerMinute }`, fire-and-forget `last_used_at = now`
   (a failed write logs `API key usage timestamp update failed` at warn and never affects the
   request), `next()`. Unexpected errors → 500 `{ error: 'Internal Server Error' }`.
2. The per-key limiter (429 when exhausted).
3. The route's existing middleware and controller, unchanged.

**Downgrade behaviour, stated precisely:** a key is never auto-revoked. If its owner's resolved plan
stops granting `USE_API` (downgrade, or a paid plan that expired and fell back to FREE), every request
with that key gets 403 `API_ACCESS_NOT_IN_PLAN`; if the plan grants `USE_API` again, the same key works
again. The owner can always list and revoke it with a session.

## 8. Authentication & Authorization

### Provider and rationale

Sessions: the existing Supabase JWT chain, unchanged. Machine access: opaque random bearer keys,
SHA-256-hashed at rest, looked up by hash. Chosen over long-lived JWTs because a key can be revoked
instantly by one row update and its owner's plan is re-read on every request.

### Flows

1. **Mint:** user signs in on the web (existing) → `POST /api/v1/auth/api-keys { name }` → 201 with
   `key` shown once → client stores it.
2. **Use:** client sends `Authorization: Bearer ck_live_…` to a procurement or analytics route →
   §5 API-key path.
3. **List / revoke:** session `GET` / `DELETE /api/v1/auth/api-keys[/:id]`.
4. **Lost key:** there is no recovery; revoke it and mint a new one.
5. **Kill switch:** operator sets `API_ACCESS` to `false` → every API-key request gets 503; sessions
   are unaffected.
6. **Account deletion:** cascades to the user's keys (FK `ON DELETE CASCADE`).

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| 7 protected procurement routes | session or API key | `procurement/presentation/routes.ts` (`authenticate`) |
| 12 analytics routes | session or API key, then `USE_ANALYTICS`, then flag `ANALYTICS` | `analytics/presentation/routes.ts` |
| `/api/v1/auth/api-keys` | session only (`requireSessionAuth` first); POST also `USE_API` | `identity/presentation/apiKeyRoutes.ts` |
| API-key path | flag `API_ACCESS`, valid unrevoked key, resolved plan grants `USE_API` | `identity/presentation/ApiKeyAuthMiddleware.ts`, `identity/application/ApiKeyService.ts` |
| notifications routes | session only, then flag `NOTIFICATIONS` | `notifications/presentation/routes.ts` |

**How "an API key cannot mint API keys" is enforced:** `requireSessionAuth` is the first handler on
all three `/api-keys` routes and answers 403 `SESSION_REQUIRED` for any request the §5 detection rule
classifies as an API key, before the JWT is parsed. As a second line, `AuthMiddleware` would reject a
`ck_live_` token as an invalid JWT anyway.

**Enforcement rule:** authorization is checked server-side on every request.

### Roles and permissions

| Plan | Can | Cannot |
|---|---|---|
| FREE | public routes, session-only routes its capabilities allow | analytics, API keys |
| STARTER | + favorites (session) | analytics, API keys |
| PROFESIONAL | + similarity, analytics (session) | API keys |
| BUSINESS | + analytics, API keys (60 req/min/key) | — |
| ENTERPRISE | + analytics, API keys (600 req/min/key) | — |

An API-key request carries the owner's roles from `users.roles` and `permissions: []` (the session
path takes both from the Supabase payload; no route in this repo reads `permissions`).

### Sessions

Unchanged for the web. API keys: no expiry, no refresh, no cookies, so no CSRF surface; revocation is
immediate because every request re-reads the row.

### Multi-tenancy / row-level isolation

Per-user, as today: every key query filters by `userId` from `req.user.id` (`listForUser`, `revoke`
uses `findFirst({ where: { id, userId } })`), and the API-key path sets `req.user` to the key's owner,
so existing controllers keep scoping by `req.user.id`. Organization-level isolation is out of scope.

## 9. BUILD ORDER

### The rules of a step

1. **One sitting per step.** At most **5 files** and **2–6 acceptance criteria** per step, with at
   least one failure or edge case.
2. **Every step carries all four fields:** `Do`, `Done when`, `Verify`, `Checkpoint`. The Checkpoint
   commits with `git add -A && git commit -m "<task-id>: <task title>"` and tags
   `step-NN-<slug>`. The task id is the step's `tasks.json` id (`E1-T1` … `E3-T6`). The repo already
   holds the notifications change's `step-*` tags; every slug here is different, so no tag collides.
3. **"Done when" conditions are observable and machine-checkable**, in EARS form.
4. **"It looks right" is banned.**
5. **`Verify` is literal shell**, run from the repository root; its exit status enforces the result.
6. **A step is not done until its own verify commands pass** *and* the previous steps' still do.
7. **Checkpoint every step.** If a step goes wrong, `git reset --hard <previous step's tag>`. For step
   1 the previous tag is `api-platform-baseline`, created by §10 Bootstrap.
8. **Never skip ahead.** If step N is blocked, stop and report.
9. **No step retroactively breaks an earlier gate.** No env var is added. The only new runtime
   dependency of existing routes is one `feature_flags` lookup, and `checkFeatureEnabled` treats a
   missing row **and** a failed lookup as enabled, so an existing test whose prisma mock has no
   `featureFlag` still passes (step 5 adds the mock line anyway). The auth swap keeps the session
   handlers byte-for-byte the same instances.
10. **Counts are counted.** 7 protected procurement routes (`procurement/presentation/routes.ts`
    lines 54–95), 6 public ones (lines 46–52), 12 analytics routes (`analytics/presentation/routes.ts`
    lines 24–35), 2 notifications routes. Every other gate asserts a property.
11. **Every `Verify` line exits 0 on a correct step.** Expected non-zero exits use
    `status=0; cmd || status=$?; test "$status" -eq N`.
12. **Every check is observable in its medium.** Types by `tsc`, behaviour by vitest, file facts by
    `grep`/`test`, built output by `node -e "require(…)"`.
13. **Built output is exercised early.** Step 2 requires the first new built module from `dist/`,
    step 8 the API-key domain, step 14 the dispatcher. Every route change is driven through Express
    by supertest in its own step.
14. **No `Verify` asserts its own Checkpoint's state.** `git diff -U0 HEAD -- <file>` compares the
    working tree with the **previous** step's commit and asserts zero removed lines.
15. **No byte-exact golden files.** Tests assert parsed JSON, status codes, `code` fields, and
    strings this blueprint's own code defines (§19.6).
16. **No gate passes on a bare non-zero exit.**

```ts
import type { PrismaClient } from '@prisma/client';
import type { FeatureFlagKey } from '../domain/featureFlags';

export type FeatureFlagReader = Pick<PrismaClient, 'featureFlag'>;

/**
 * Default-open kill switch.
 * Rules:
 * - No row for the key = enabled (a flag not yet created never changes behaviour).
 * - A row with enabled = true = enabled.
 * - Only a row with enabled = false disables the feature.
 */
export const isFeatureEnabled = async (client: FeatureFlagReader, key: FeatureFlagKey): Promise<boolean> => {
  const flag = await client.featureFlag.findUnique({ where: { key }, select: { enabled: true } });
  return flag === null || flag.enabled;
};
```

Create `backend/src/modules/platform/presentation/requireFeatureEnabled.ts` (the `requireCapability`
style):

```ts
import { Request, Response, NextFunction } from 'express';
import { prisma } from '../../../infrastructure/db/prisma';
import { logger } from '../../../infrastructure/logger';
import { isFeatureEnabled } from '../application/isFeatureEnabled';
import { FEATURE_DISABLED_RESPONSE, FeatureFlagKey } from '../domain/featureFlags';

/**
 * Fail-open lookup: if the flag cannot be read, the feature stays on and a warning is logged.
 */
export const checkFeatureEnabled = async (key: FeatureFlagKey): Promise<boolean> => {
  try {
    return await isFeatureEnabled(prisma, key);
  } catch (error) {
    logger.warn('Feature flag lookup failed, treating as enabled', {
      key,
      error: error instanceof Error ? error.message : String(error),
    });
    return true;
  }
};

export const requireFeatureEnabled = (key: FeatureFlagKey) => {
  return async (req: Request, res: Response, next: NextFunction) => {
    if (!(await checkFeatureEnabled(key))) {
      return res.status(503).json({ ...FEATURE_DISABLED_RESPONSE });
    }

    next();
  };
};
```

```ts
import { createHash, randomBytes } from 'node:crypto';

export const API_KEY_PREFIX = 'ck_live_';
export const API_KEY_RANDOM_BYTES = 32;
export const API_KEY_DISPLAY_PREFIX_LENGTH = 12;
export const API_KEY_PATTERN = /^ck_live_[A-Za-z0-9_-]{43}$/;

export interface GeneratedApiKey {
  plaintext: string;
  keyPrefix: string;
  keyHash: string;
}

/** What ApiKeyAuthMiddleware attaches as `(req as any).apiKey` for the per-key limiter. */
export interface ApiKeyRequestContext {
  id: string;
  apiRequestsPerMinute: number | null;
}

/** One-way SHA-256 (lowercase hex). A 256-bit random key needs no slow password hash. */
export function hashApiKey(plaintext: string): string {
  return createHash('sha256').update(plaintext, 'utf8').digest('hex');
}

export function generateApiKey(): GeneratedApiKey {
  const plaintext = API_KEY_PREFIX + randomBytes(API_KEY_RANDOM_BYTES).toString('base64url');
  return {
    plaintext,
    keyPrefix: plaintext.slice(0, API_KEY_DISPLAY_PREFIX_LENGTH),
    keyHash: hashApiKey(plaintext),
  };
}

/** The token after the exact, case-sensitive `Bearer ` prefix, or null. */
export function extractBearerToken(authorization: string | undefined): string | null {
  if (!authorization || !authorization.startsWith('Bearer ')) return null;
  return authorization.slice('Bearer '.length);
}

/**
 * True only for `Bearer ck_live_…`. A Supabase JWT starts with `eyJ`, so it can never match.
 */
export function isApiKeyAuthorization(authorization: string | undefined): boolean {
  const token = extractBearerToken(authorization);
  return token !== null && token.startsWith(API_KEY_PREFIX);
}
```

```ts
}

export class ApiKeyService {
  constructor(
    private readonly prisma: ApiKeyClient,
    private readonly now: () => Date = () => new Date(),
  ) {}

  /**
   * Resolves a presented key to its owner under the same plan rules as a web session.
   * Throws ApiKeyAuthenticationError (malformed, unknown, revoked) or
   * ApiAccessNotAllowedError (owner's resolved plan lacks USE_API).
   */
  async authenticate(plaintextKey: string): Promise<ApiKeyAuthentication> {
    if (!API_KEY_PATTERN.test(plaintextKey)) throw new ApiKeyAuthenticationError();

    const apiKey = await this.prisma.apiKey.findUnique({
      where: { keyHash: hashApiKey(plaintextKey) },
      include: { user: { include: { plan: { include: { capabilities: { include: { capability: true } } } } } } },
    });
    if (!apiKey || apiKey.revokedAt) throw new ApiKeyAuthenticationError();

    const { user, apiRequestsPerMinute } = await buildAuthenticatedUserFromDbUser(
      apiKey.user,
      () => this.prisma.plan.findUnique({
        where: { name: 'FREE' },
        include: { capabilities: { include: { capability: true } } },
      }),
      this.now(),
    );

    if (!user.capabilities?.includes(USE_API_CAPABILITY)) throw new ApiAccessNotAllowedError();

    return { apiKeyId: apiKey.id, user, apiRequestsPerMinute };
  }

  async recordUsage(apiKeyId: string): Promise<void> {
    await this.prisma.apiKey.update({ where: { id: apiKeyId }, data: { lastUsedAt: this.now() } });
  }
}
```

```ts
import { FEATURE_DISABLED_RESPONSE, FEATURE_FLAGS, FeatureFlagKey } from '../../platform/domain/featureFlags';

export interface ApiKeyAuthenticator {
  authenticate(plaintextKey: string): Promise<ApiKeyAuthentication>;
  recordUsage(apiKeyId: string): Promise<void>;
}

export class ApiKeyAuthMiddleware {
  constructor(
    private readonly apiKeys: ApiKeyAuthenticator,
    private readonly isFeatureEnabled: (key: FeatureFlagKey) => Promise<boolean>,
  ) {}

  /**
   * Express middleware for `Authorization: Bearer ck_live_…` requests. Attaches the same
   * AuthenticatedUser shape CurrentUserResolver builds, plus `req.apiKey` for the per-key limiter.
   */
  handle = async (req: Request, res: Response, next: NextFunction) => {
    try {
      if (!(await this.isFeatureEnabled(FEATURE_FLAGS.API_ACCESS))) {
        return res.status(503).json({ ...FEATURE_DISABLED_RESPONSE });
      }

      const token = extractBearerToken(req.headers.authorization) ?? '';
      const result = await this.apiKeys.authenticate(token);
      const apiKey: ApiKeyRequestContext = { id: result.apiKeyId, apiRequestsPerMinute: result.apiRequestsPerMinute };

      (req as any).user = result.user;
      (req as any).apiKey = apiKey;

      this.apiKeys.recordUsage(result.apiKeyId).catch((error: unknown) => {
        logger.warn('API key usage timestamp update failed', {
          apiKeyId: result.apiKeyId,
          error: error instanceof Error ? error.message : String(error),
        });
      });

      next();
    } catch (error) {
      if (error instanceof ApiKeyAuthenticationError) {
        return res.status(401).json({ error: error.message, code: error.code });
      }
      if (error instanceof ApiAccessNotAllowedError) {
        return res.status(403).json({ error: error.message, code: error.code });
      }
      logger.error('API key authentication error', { error: error instanceof Error ? error.message : String(error) });
      return res.status(500).json({ error: 'Internal Server Error' });
    }
  };
}
```

```ts
import { Request, Response, NextFunction, RequestHandler } from 'express';
import { isApiKeyAuthorization } from '../domain/ApiKey';

export const SESSION_REQUIRED_RESPONSE = {
  error: 'Las claves de API no pueden administrar claves de API. Usa tu sesión de la aplicación web.',
  code: 'SESSION_REQUIRED',
} as const;

/** Runs Express handlers in order; stops when one responds without calling next(). */
export const runHandlers = (handlers: RequestHandler[], req: Request, res: Response, done: NextFunction): void => {
  let index = 0;
  const step = (error?: unknown): void => {
    if (error) {
      done(error);
      return;
    }
    const handler = handlers[index++];
    if (!handler) {
      done();
      return;
    }
    try {
      const result: unknown = handler(req, res, step);
      if (result instanceof Promise) result.catch(done);
    } catch (thrown) {
      done(thrown);
    }
  };
  step();
};

export interface AuthenticateApiKeyOrSessionDeps {
  apiKeyHandlers: RequestHandler[];
  sessionHandlers: RequestHandler[];
}

/**
 * `Authorization: Bearer ck_live_…` → the API-key handlers; anything else → the session
 * handlers, unchanged (they keep answering exactly as before for a missing or invalid header).
 */
export const createAuthenticateApiKeyOrSession = ({ apiKeyHandlers, sessionHandlers }: AuthenticateApiKeyOrSessionDeps): RequestHandler =>
  (req, res, next) =>
    runHandlers(isApiKeyAuthorization(req.headers.authorization) ? apiKeyHandlers : sessionHandlers, req, res, next);

/** First handler on key-management routes: an API key can never mint, list or revoke keys. */
export const requireSessionAuth: RequestHandler = (req, res, next) => {
  if (isApiKeyAuthorization(req.headers.authorization)) {
    res.status(403).json({ ...SESSION_REQUIRED_RESPONSE });
    return;
  }
  next();
};
```

```ts
import { Request, Response } from 'express';
import { logger } from '../../../infrastructure/logger';
import { ApiKeyNotFoundError } from '../domain/errors';
import type { ApiKeySummary, IssuedApiKey } from '../application/ApiKeyService';
import { ApiKeyIdSchema, CreateApiKeySchema } from './ApiKeySchemas';

export interface ApiKeyManager {
  issue(userId: string, name: string): Promise<IssuedApiKey>;
  listForUser(userId: string): Promise<ApiKeySummary[]>;
  revoke(userId: string, apiKeyId: string): Promise<ApiKeySummary>;
}

const notFound = (res: Response) => {
  const error = new ApiKeyNotFoundError();
  return res.status(404).json({ error: error.message, code: error.code });
};

export class ApiKeyController {
  constructor(private readonly apiKeys: ApiKeyManager) {}

  async create(req: Request, res: Response) {
    const user = (req as any).user;
    if (!user) return res.status(401).json({ error: 'Unauthorized' });

    const parsed = CreateApiKeySchema.safeParse(req.body);
    if (!parsed.success) {
      return res.status(400).json({ error: 'Validation failed', details: parsed.error.format() });
    }

    try {
      const issued = await this.apiKeys.issue(user.id, parsed.data.name);
      return res.status(201).json(issued);
    } catch (error) {
      return this.fail(res, user.id, error);
    }
  }

  async list(req: Request, res: Response) {
    const user = (req as any).user;
    if (!user) return res.status(401).json({ error: 'Unauthorized' });

    try {
      const apiKeys = await this.apiKeys.listForUser(user.id);
      return res.status(200).json({ apiKeys });
    } catch (error) {
      return this.fail(res, user.id, error);
    }
  }

  async revoke(req: Request, res: Response) {
    const user = (req as any).user;
    if (!user) return res.status(401).json({ error: 'Unauthorized' });

    const parsed = ApiKeyIdSchema.safeParse(req.params.id);
    if (!parsed.success) return notFound(res);

    try {
      const summary = await this.apiKeys.revoke(user.id, parsed.data);
      return res.status(200).json(summary);
    } catch (error) {
      if (error instanceof ApiKeyNotFoundError) return notFound(res);
      return this.fail(res, user.id, error);
    }
  }

  private fail(res: Response, userId: string, error: unknown) {
    logger.error('API key endpoint error', { userId, error: error instanceof Error ? error.message : String(error) });
    return res.status(500).json({ error: 'Internal Server Error' });
  }
}
```

```bash

#                existing agent files → merge self-check → bundle commit → baseline tag → install

d=$(git diff --numstat HEAD -- AGENTS.md | cut -f2); test "${d:-0}" -le 1   # expect: exit 0 — same rule for AGENTS.md
```

This block starts no service and applies no migration; no §9 gate needs Postgres, Redis or the
network. Every line is non-interactive and safe to run twice: on a second run `rsync` skips and exits
0, each `grep -qF … ||` matches and skips the copy, the three `numstat` checks see an empty diff
(`${d:-0}` = 0), the cached-diff guard skips the commit, and the tag guard skips the tag. On BSD/macOS
and GNU alike none of these guards exits non-zero on its no-op path. **Never overwritten once
present:** `CLAUDE.md`, `AGENTS.md`, `.claude/settings.json` (after the first merge), every rule and
skill file, `backend/package.json`, `backend/package-lock.json` — `workspace/` carries no package
manifest.

**Recovery from a partial first run.** If the first Bootstrap run stopped after the copy/merge lines
but before the bundle commit (a `numstat` check failed, a commit hook rejected the commit, or the
session died), the tree is dirty with files Bootstrap itself wrote, and the clean-tree precondition
refuses to start a retry. Before retrying, the operator resets exactly that set, from the repository
root:

1. Restore the three merged-in-place files to their last committed state:
   `git checkout -- CLAUDE.md AGENTS.md .claude/settings.json`
2. Remove the untracked new files this bundle's Bootstrap introduces:
   `rm -f .claude/rules/api-keys.md .claude/rules/feature-flags.md .claude/rules/prisma-new-tables.md`
   and `rm -rf .claude/skills/add-feature-flag/`
3. Confirm the precondition now holds — `test -z "$(git status --porcelain -- . ':!blueprints')"`
   exits 0 — then fix the cause the failed line reported and re-run the whole Bootstrap block from
   its first line.

Only these seven paths are touched; anything else the precondition still reports is unrelated work
to commit or stash, never to delete. This reset is not needed once the bundle commit exists: from
then on the tree is clean and the block re-runs as described above.

**Permissions.** This block is run by an operator, once, before the builder starts. Its copy, commit
and tag lines (`rsync`, the merge `cp` lines, `git add`, `git commit`, `git tag`) are not in the
repository's current `.claude/settings.json`; the entries that cover them arrive with the merged
`settings.json` this same block copies in, so on the first run they prompt for permission. That is
expected, not a defect. The §9 `Verify` lines and §20.1's automated (non-manual) lines are the ones

**Feature-flag runbook (database only):**

```sql
UPDATE feature_flags SET enabled = false, updated_at = now() WHERE key = 'API_ACCESS';   -- kill all API-key traffic
UPDATE feature_flags SET enabled = true,  updated_at = now() WHERE key = 'API_ACCESS';   -- restore
INSERT INTO feature_flags (key, enabled, description, updated_at) VALUES ('ANALYTICS', false, 'manual', now())
  ON CONFLICT (key) DO UPDATE SET enabled = EXCLUDED.enabled, updated_at = now();         -- when the row was never seeded
```

Effect is immediate (no cache): the next request reads the row.

**Revoke a leaked key without the owner:**
`UPDATE api_keys SET revoked_at = now() WHERE key_prefix = 'ck_live_XXXX' AND revoked_at IS NULL;`
(check the `user_id` first; prefixes are not unique).

and column stay, unused and harmless.

**Rollback, schema** (only after the code rollback is live; discards every key and flag):

```sql
DROP TABLE IF EXISTS "feature_flags";
ALTER TABLE "plans" DROP COLUMN IF EXISTS "api_requests_per_minute";
DELETE FROM "_prisma_migrations" WHERE migration_name = '20261121000000_add_api_keys_and_feature_flags';
```

## 14. Security & Secrets

| Concern | Control | Implemented in |
|---|---|---|
| Secret storage | API keys stored only as SHA-256 `key_hash` plus a 12-char `key_prefix`. Plaintext exists only in the 201 response | `ApiKeyService.issue`, `api_keys` |
| Key entropy | 32 random bytes (256 bits) from `randomBytes`, base64url | `domain/ApiKey.ts` |
| Brute force / timing | Lookup is by the hash of the presented key through a unique index; no prefix or partial match is ever compared, so response timing reveals nothing about stored keys. Malformed tokens are rejected before any query | `ApiKeyService.authenticate` |
| Secret rotation | Users revoke and re-mint; operators revoke by SQL (§12); `API_ACCESS` kills all key traffic at once | §12 runbook |
| Input validation | `z.strictObject({ name })` on POST; UUID shape check on `:id`; key pattern check before hashing | `ApiKeySchemas.ts`, `ApiKeyService.ts` |
| Output encoding / XSS | JSON only | — |
| SQL injection | Prisma parameterized queries; static migration SQL | all new code |
| AuthN / AuthZ | §8. Key management is session-only (`requireSessionAuth`); minting needs `USE_API`; each API-key request re-checks revocation and `USE_API` | `apiKeyRoutes.ts`, `ApiKeyAuthMiddleware.ts` |
| Enumeration | Another user's key id → 404, same as a missing one | `ApiKeyService.revoke`, `ApiKeyController.revoke` |
| CSRF | Bearer tokens, no cookies | — |
| Rate limiting / abuse | Per key: plan `api_requests_per_minute` (fallback 10) per 60 s, `rl:apikey:`. Key management: 10/min/IP, `rl:api-keys:`. Global 500/15 min/IP unchanged | `apiKeyRateLimiter.ts`, `identity/presentation/routes.ts`, `server.ts` |
| Webhook verification | NOT APPLICABLE — no webhooks | — |
| Dependency audit | No new dependencies; `(cd backend && npm audit --omit=dev)` stays manual | — |
| Security headers | Unchanged (`helmet()`) | `server.ts` |
| PII handling | No new personal data. `api_keys.name` is a user label; rows cascade-delete with the user | `schema.prisma` |
| Logging hygiene | Never log a key, its hash, its prefix or the `Authorization` header. Log only `apiKeyId` and `userId`. morgan `combined` does not log request headers; `AuditMiddleware` logs `userId` only | `.claude/rules/api-keys.md` |

**Hard rules**

- No secret is ever committed, logged, or returned except the caller's own new key in the 201 response.
- Authorization checks run before the work: `requireSessionAuth` and the session chain before the
  controller; the flag, revocation and `USE_API` checks before `req.user` is set.
- Transport: keys are bearer credentials and must only be sent over TLS in production (§20.2).

Regulated data: none new. The product operates in Colombia under Ley 1581 de 2012; this change adds no
personal data category.

````markdown
# Add a feature flag

## When to use

- A route or a whole path (like API-key auth) must be switchable off in production by one SQL `UPDATE`.
- Not for per-plan access: that is a capability (`requireCapability`) seeded in `backend/prisma/seed.ts`.

## Steps

1. Add the key to `FEATURE_FLAGS` in `backend/src/modules/platform/domain/featureFlags.ts` (UPPER_SNAKE_CASE, value equal to the key). `FeatureFlagKey` updates itself.
2. In the router, add `const require<Name>Enabled = requireFeatureEnabled('<KEY>');` (import from `../../platform/presentation/requireFeatureEnabled`) and insert it **after** the auth chain and any limiter, before validation, so unauthenticated callers keep getting 401 and capability failures keep getting 403. Never remove or reorder existing middleware.
3. In a non-route path, call `checkFeatureEnabled('<KEY>')` and answer `{ ...FEATURE_DISABLED_RESPONSE }` with 503 when it is false.
4. Seed the row in `backend/prisma/seed.ts` by adding one entry to the `featureFlags` array (`enabled: true`). The loop already upserts with `update: {}`, so a re-seed never re-enables a disabled flag. Insert lines only.
5. Test with supertest: flag row `{ enabled: false }` → 503 `code: 'FEATURE_DISABLED'`; no row → normal response; no auth → 401. Add the key to the `featureFlagUpserts` assertion in `backend/src/__tests__/seed.test.ts`.

## Verify

```bash
(cd backend && npx vitest run src/modules/platform)          # expect: exit 0
(cd backend && npx vitest run src/__tests__/seed.test.ts)    # expect: exit 0
(cd backend && npx tsc --noEmit)                             # expect: exit 0
```

## Do not

- Add an endpoint or UI that writes `feature_flags`. Flags are database-only by decision.
- Treat a missing row as disabled. Default-open is the contract.
- Cache flag values in memory. The kill switch must take effect on the next request.
````

```markdown
# API keys

- Format: `ck_live_` + `randomBytes(32).toString('base64url')` (43 chars), pattern `^ck_live_[A-Za-z0-9_-]{43}$`. Stored: `key_hash` = lowercase hex SHA-256 of the full key, `key_prefix` = first 12 chars. `node:crypto` only — no bcrypt/argon2.
- Detection: API-key path if and only if the header starts with the exact `Bearer ` and the token starts with `ck_live_` (`isApiKeyAuthorization`). Everything else takes the unchanged session chain. A malformed `ck_live_` token is 401 `INVALID_API_KEY`, never a session fallback.
- `ApiKeyAuthMiddleware.handle` order: `API_ACCESS` flag (503) → `ApiKeyService.authenticate` (401 malformed/unknown/revoked, 403 `API_ACCESS_NOT_IN_PLAN`) → set `req.user` (an unchanged `AuthenticatedUser`) and `req.apiKey = { id, apiRequestsPerMinute }` → fire-and-forget `recordUsage` (warn on failure) → `next()`.
- Plan rules for API-key users live only in `application/ApiKeyUserMapper.ts` and must match `CurrentUserResolver` exactly (expired or missing plan → FREE row). Change one, change both, and keep `ApiKeyUserMapper.test.ts`'s parity cases green. Never edit `CurrentUserResolver.ts` or `AuthenticatedUser.ts`.
- The API-key path never sets `organizationId`, `avatarUrl`, `lastLoginAt` or `metadata`; `permissions` is `[]`.
- Per-key limiter: `createApiKeyRateLimiter(new FallbackRedisStore(redisAppClient, 'rl:apikey:'))`, created once in `apiKeyAuth.ts`, `keyGenerator` = key id, `limit` = `req.apiKey.apiRequestsPerMinute` (fallback 10, never unlimited). Never change an existing IP limiter.
- Routes reachable by key: wrap the router's own session pair, `authenticateApiKeyOrSession([authMiddleware.handle, currentUserResolver.resolve])`. Public routes never gain auth.
- Key management `/api/v1/auth/api-keys`: `requireSessionAuth` first on every route; POST also `requireCapability('USE_API')`; another user's key id → 404 `API_KEY_NOT_FOUND`, never 403.
- HTTP mapping: `ApiKeyAuthenticationError` → 401, `ApiAccessNotAllowedError` → 403, `ApiKeyNotFoundError` → 404, each `{ error, code }`; anything else → 500 `{ error: 'Internal Server Error' }`.
- Never log the `Authorization` header, a key, its hash or its prefix. Log `apiKeyId` and `userId` only. The plaintext leaves the server once: the 201 of `POST /api/v1/auth/api-keys`.
```
